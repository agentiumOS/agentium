## Finding

The smallest coherent addition is a `GraphStep` and explicitly bounded `RepeatStep` alongside the existing `StepDef` variants. Reuse StepRunner's owned-patch result internally, the existing Agent and function leaf execution, RunContext, and neutral ExecutionServices. Keep graph scheduling separate from the Agent's model/tool loop. Keep Workflow's current top-level checkpoint boundary and accurately describe continuation as fresh remaining work.

This supports dependency scheduling and rebuilding a graph at a bounded loop boundary without changing Workflow into a second lifecycle owner or claiming per-node durable recovery. There is already a durable task/action subsystem in this base; use it for a later explicit recovery adapter instead of inventing another generic intent/receipt ledger. That subsystem is currently disconnected from Workflow, Agent's ExecutionServices and the local harness driver lifecycle.

## Durable facilities already in the pinned base

An update callback is synchronous and may be reevaluated; it cannot perform effects. `packages/core/src/durable/types.ts:32`, `:83`, `:102`, `:105`; `packages/core/src/durable/store.ts:131`. `DurableTaskSupervisor` leases/fences work, polls cancellation, limits task attempts, records monotonic token/cost reservations and waits for its action ledger to quiesce. `DurableActionLedger` already supplies the effect identity contract missing from generic dispatch: stable host-chosen action ID, canonical prepared hash over destination/arguments/connector/policy/grants/identity, stable derived idempotency key, atomic dispatch intent, confirmed result references, unknown outcomes and connector reconciliation. A dispatched exception remains unknown. `packages/core/src/durable/actions.ts:14`, `:21`, `:54`, `:69`, `:80`, `:114`, `:147`, `:173`, `:190`. `DurableRunRecords` persists bounded events and digest-checked JSON snapshots/artifact references. JournaledDurableTaskStore journals task-state transitions in the same task CAS. Source search found no integration of DurableActionLedger, DurableTaskSupervisor or DurableRunRecords in Workflow/Agent ExecutionServices/the local harness driver. Therefore the honest initial contract remains boundary continuation. A future adapter can put graph runtime state in a versioned bounded task extension, use fenced updates for per-node result/plan commits and route supported effects through the existing action ledger. Generic shell/email/payment tools remain unsupported for automatic recovery until they have an explicit connector contract.

| Option | Advantage | Concrete limitation |
|---|---|---|
| Lower a static DAG into existing serial parallel groups | Almost no leaf execution changes; natural barrier checkpoints. | Cannot derive owned patches through the public executeSteps result; global accumulated state leaks unrelated outputs; topology and skip gates remain opaque. Dynamic graph construction, blocked dependencies and ancestry still need new code. |
| Add GraphStep and RepeatStep to StepRunner | Smallest first-party extension; preserves Workflow, existing adapter, lifecycle and checkpoint shape; graph nodes can contain existing composite steps. | Needs a compiler/scheduler, scoped node identity and shared internal patch outcome. | Add a separate core ExecutionGraph class plus harness adapter | Clean graph-specific results and later recovery schema. | Adds lifecycle/registry/public API decisions before they are needed. | Implement a custom harness ExecutionDriver | Already possible through the open driver and approved registry reference. Good for a graph-specific host integration. | Does not add ordinary core Workflow graph support. Durable:true is rejected; neutral dispatch still lacks graph attempt/effect identity. |

Recommend the additive step design for boundary-only graphs, with a shared internal `StepExecution` contract carrying `state`, `patch` and `results` (`packages/core/src/workflow/step-runner.ts:7`). Do not make private StepRunner details a public API solely for reuse. Keep generated/portable graph definitions as data plus approved host executors; local callbacks stay local. A durable graph runtime is a separate adapter capability, with additional acceptance evidence, rather than an automatic side effect of accepting a graph definition.

## Contract review of the candidate GraphStep

The parent candidate is `graph: WorkflowGraphNode[] | ((state) => WorkflowGraphNode[])`, positive finite maxNodes/maxConcurrency, merge default error or explicit declaration_order; nodes contain `id`, `step`, control `dependsOn` and data `inputsFrom`. The following decisions make that candidate concrete.

### Topology and input ancestry

1. Validate each materialized graph before any child effect: unique nonempty IDs, known references, no self edges, finite configured bounds and a DAG over the union of control and data edges. Count and validate callback output at runtime; TypeScript does not validate restored/model-generated arrays. Decide whether duplicate edges normalize or reject. Validate nested graph/step structure or impose an expansion-depth bound so cyclic object references cannot recurse indefinitely.
2. Control dependencies gate readiness; done/skipped satisfy the gate and an error blocks it. Data dependencies gate readiness and require done. An inputsFrom edge is also a scheduling dependency, even if absent from dependsOn.
3. Build each node's supplied state from the graph-entry base plus owned patches of its transitive data ancestors only, in stable topological order with declaration index as tie-break. Control-only ancestors contribute no payload. Runtime injection dependencies in RunOpts are credentials/host bindings and have no graph-edge meaning.
4. Define write comparability using the union dependency graph, while defining visible ancestry using only data edges. For final graph state and each node input, writes from ordered ancestors may overwrite in the declared order. Incomparable colliding writes fail in error mode; declaration_order is an explicit alternative. Do not permit settlement order to choose a winner. Same-value writes count as owned writes.
5. No shared incremental global state should be handed to a newly ready node. That would expose unrelated completed branches and make inputs completion-order-dependent. Treat per-node result/patch records as immutable once committed.

Representative edge table:

| Edge | Readiness | Payload supplied to target |
|---|---|---|
| research-A inputsFrom join | research-A must be done | A's patch and its data ancestors |
| research-B inputsFrom join | research-B must be done | B's patch and its data ancestors |
| authorization dependsOn publish | authorization done/skipped | No authorization patch through this edge |
| join inputsFrom publish | join must be done | Join's patch and its data ancestors |

The logical ancestry contract does not imply physical confinement. Existing branch snapshots are shallow; a function can mutate nested input or access captured objects. If graph input isolation is to be enforced, use a graph-specific clone/freeze/data validator and specify compatibility for callable/opaque state. Do not silently change all Workflow state to a JSON-only format. The current documented ownership discipline is the lowest-impact alternative, but it must be presented as a trusted callback contract.

### Deterministic scheduling, conflicts and results

Stable sorting of currently ready nodes is insufficient to guarantee stable admission under a work-conserving scheduler: a fast A can admit A's descendant before B's descendant; shared budget exhaustion can then choose a different winner. The smallest deterministic implementation is ready-frontier waves sorted by stable topology/declaration order, with bounded fixed chunks, settlement of already-started nodes and a commit/join barrier before advancing. The cost is waiting for unrelated slow siblings. An incremental scheduler is viable if the declared guarantee is stable inputs/conflicts/results, while outbound admission order remains concurrency-dependent.

Graph node IDs must be carried in results and attempt metadata. Existing workflow.step events carry only runId/stepName/status (`packages/core/src/events/types.ts:101`); Agent sessions are derived from step.name (`packages/core/src/workflow/step-runner.ts:121`). Unique graph IDs do not prevent duplicate step names from sharing a child session. Scope child sessions by graph location/node ID and ensure nested graphs/repeated iterations are distinguishable. Preserve a logical node identity separately from a fresh execution/attempt ID.

A blocked node needs a stable recorded reason such as failed_control_dependency, failed_data_dependency or skipped_data_dependency. It may map to the existing skipped StepResult status for compatibility, but it must not appear to have executed. Decide aggregate outcome when a skipped data dependency blocks a required terminal: an upstream false condition alone should not accidentally yield a successful publish outcome. A failed ancestor already produces an aggregate error; pure skip propagation needs an explicit completion rule.

Strict conflict is a structural failure. Settle all started work before reporting it, apply none of the failed join's patches to its parent, record completed external effects as evidence and admit no downstream work. The graph can preserve per-node records in memory for diagnostics while keeping its parent-state update atomic. Do not describe this as rolling back effects.

### Cancellation and ownership

Check cancellation before materializing the graph, before each dispatch, after builder/predicate results, after every child settles and before state/checkpoint commit. Synchronous callbacks cannot be preempted; no late callback/child result may advance the run after abort is known. All already-started children remain owned and must settle before their Agent/resource/session owners are released. The current StepRunner and harness enforce cooperative barriers; neither can promise bounded shutdown for a tool/function ignoring its signal.

Use the graph node's immutable attempt context for StepRunner events and Agent child metadata. Function dispatch currently uses `dispatchEffect(name,args,execute)` without an optional context, while the harness implementation always runs policy/observation with the root context and a fresh random toolCallId (`packages/core/src/agent/execution-services.ts:60`; `packages/harness/src/runtime/driver.ts:1548`, `:1566`). `dispatch` has the same missing context parameter. Passing node metadata only to step.run does not automatically attribute host tool policy/receipts to the node. If per-node causal attribution is promised, add a backward-compatible context/request identity option or an explicit graph effect adapter; metadata alone is not a stable intent ledger.

## Bounded repeat, repair and replan

The candidate RepeatStep is `repeat: StepDef[]`, `while(state,iteration): boolean`, `maxIterations: positive integer`. Specify iteration as zero-based completed-body count. Evaluate before the first body; false performs zero work. After each completed body evaluate the next guard on the resulting state. At maxIterations, a still-true guard returns a stable exhaustion error without another body dispatch; false completes. Specify the resulting repeat patch and child results, and whether ordinary errors under failurePolicy:continue allow another iteration. Strict conflict/cancellation must always escape; failurePolicy:stop must prevent another loop body.

Repeating a GraphStep builder provides boundary replanning: the callback sees the previous completed iteration's observations and materializes the next bounded DAG. This is a useful limited contract. It does not rewrite the topology of running nodes or restart a failed parallel sibling. Builder invocation count is bounded by the outer repeat, maxNodes counts each graph materialization, and maxConcurrency counts graph node execution slots; it does not cap tools inside concurrent Agent/composite nodes. Document those units. Nested repeats/graphs need either a total expansion bound or an explicit statement that local bounds multiply. Shared host model/tool/token/deadline admission still applies.

Model-directed repair should be a new bounded decision rather than an invisible transport retry. Use an explicitly bound controlled model role and validate its plan/patch output before child effects. Harness controlModel already provides tool-free, grant-bound shared-budget policy calls (`packages/harness/src/runtime/driver.ts:1248`, `:1261`, `:1278`, `:1301`), but core should consume a host callback or neutral model operation rather than import this harness method.

For future in-flight replanning, constrain edits to pending nodes at a quiescent commit boundary. Retain completed node definitions/inputs/results and causal ancestry. Reject edits that invalidate running/completed node inputs; otherwise the adapter must fence superseded attempts, cancel their children, retain late-result/effect evidence and explicitly handle downstream invalidation. Attach a plan revision, parent revision, validated change and attempt epoch to each committed transition. A fresh output correction does not erase a confirmed effect. That larger contract is not supplied by invoking a builder every time a GraphStep is entered.

## Resume and side-effect claims

Initial GraphStep/RepeatStep support can truthfully retain existing Workflow continuation: a completed top-level graph/repeat is skipped on continuation, later top-level work executes afresh, and nested successful siblings inside an incomplete boundary have no recovery record. Continuing from an earlier saved boundary can execute those siblings again. Boundary checkpoint failure can occur after the effect applied. Preserve the current no-auto-retry-under-services rule and describe this loss window directly.

A future per-node recovery adapter needs versioned graph topology/materialized plan, stable graph/node/effect identities, input digests, node output/patch references, dependency/route decisions, completed-node records, attempt state/fence, repair/iteration counters and retained root budget/deadline semantics. Validate restored state and approved code/binding versions before any effect. Recorded upstream model/tool outputs must drive resumed downstream decisions; fresh model sampling is new execution. Read-only history inspection should make zero calls. Deliberate fork/reexecution must declare its effect-identity policy.

The existing DurableTaskStore/actions/records supply storage and intent machinery, but the graph adapter still has to connect them: atomic fenced node-result plus scheduler-state updates; connector-backed effect dispatch; reconciliation before uncertain retry; blob/reference expiry/corruption handling; explicit old-schema rejection or migration. The action ledger's stable ID must be tied to logical effect intent and unchanged inputs, not a new node attempt UUID. A reused action ID with changed arguments must fail, as the existing ledger already does. Arbitrary Agent-issued calls cannot automatically acquire these guarantees merely from a node checkpoint.

Harness session `replayable` and retained conversations are not such an adapter: its snapshot has history/state/revision and an external-store lease contract, while the local event store is bounded in-process history. `packages/harness/src/runtime/session-bindings.ts:7`, `:19`, `:32`, `:40`; `packages/harness/src/runtime/events.ts:76`. Do not use durable driver capability flags or exact-playback wording until a recovery adapter actually implements the complete contract.

## Decisions to carry into the specification

- Confirm boundary replanning via RepeatStep is the requested first dynamic capability; distinguish it from live topology replacement.
- Define data ancestry using only inputsFrom edges, and conflict comparability using the scheduling union; use stable topology/declaration order everywhere.
- Choose ready-wave admission for deterministic budget winners or explicitly permit concurrency-dependent admission while preserving deterministic inputs/joins.
- Decide graph-specific deep isolation versus documented owned-patch discipline, and compatibility for opaque/callable state.
- Record blocked reasons and the completion requirement for skipped data branches; preserve cancellation/structural-failure behavior.
- Specify maxIterations guard semantics and local/global limits; maxConcurrency cannot be advertised as a root tool concurrency ceiling.
- Add node/iteration/attempt attribution without conflating it with durable effect intent. Reuse existing action ledger only through an explicit supported recovery connector/adapter.
- Preserve boundary-only continuation and durable:false until stronger recovery behavior is implemented and exercised.
