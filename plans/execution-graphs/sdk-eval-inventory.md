## Recommended scope

Keep `Workflow` as the orchestration API and retain the ordinary bounded `Agent` loop for node reasoning/tool use and repair. Reuse `workflowDriver` and the neutral `ExecutionServices` port. Existing public contracts already provide typed serial state, conditional steps, parallel groups, failure policies, cancellation, owned patches, strict conflicts and completed-boundary continuation. Those capabilities alone do not justify a second graph class, driver, evaluation execution loop, graph database or graph library.

The useful differentiating case is an explicit dependency DAG with shared prerequisites and successors that should not wait for unrelated work. For example: start A and B; C depends only on A; D depends on A and B; E depends on C and D. C must start while B is still running, and D must start after B while C is still running. A tree composed from today's nested serial/parallel groups introduces an extra barrier or repeats A. A scheduler that runs complete topological levels also introduces an extra barrier. Demonstrating this case would justify one opt-in graph definition capability; serial examples and ordinary fan-out/join do not establish the need.

The smallest candidate public surface is a graph group added to `StepDef`, containing named existing steps, dependency references, a finite concurrency cap and the existing merge vocabulary. A group would remain one top-level Workflow checkpoint boundary. This is a proposal for design review, not an implemented type or a settled scheduler contract. It avoids changing the meaning of existing `steps`, constructor callers, state patches, named Agent output fields or checkpoint cursors. A separate `WorkflowConfig` graph mode is possible, but requires more result/cursor/documentation decisions and should not be introduced alongside a graph group without a concrete consumer.

First-version graph-native cycles are not necessary to evaluate the DAG benefit. Bounded repair can stay inside an existing Agent node or an explicitly bounded host routine. If graph-native repeat is required by the final specification, it needs an explicit finite visit/iteration bound shared with aggregate budgets and a documented terminal reason; a dependency cycle must never silently become an executable unbounded loop. Reject unsupported cycles before effects. Do not reset Agent bounds or harness budgets on each repair attempt.

## Compatibility decisions that need an explicit specification

1. **Definition identity and validation.** Stable unique node names, known dependency references, nonempty valid IDs, cycle policy and finite concurrency/repeat limits must be validated before any node effect. Today's graph-less contracts do not supply these rules. Validate external checkpoint state through the existing validator; a TypeScript assertion cannot validate restored input.
2. **State visible to a newly ready node.** The spec must choose deterministic dependency-derived state or a clearly defined shared-state policy. Dispatch/settlement order must not silently determine whether a node sees unrelated sibling writes. Reuse owned patches; preserve deliberate same-value writes and replace nested objects rather than mutate shared references. Do not introduce a reducer framework merely to implement the existing merge rules.
3. **Branch and join readiness.** Existing conditions may produce skipped work; a graph join must not wait forever on an excluded branch. Define exactly which selected/completed prerequisites admit a successor, what a skipped prerequisite means, and which descendants are skipped after failure. An “all settled” join must not treat a failed required input as successful evidence.
4. **Failure policy compatibility.** Ordinary Workflow `continue` still runs later serial work after a collected error. For dependency nodes, continuing independent work does not imply running consumers of failed required prerequisites. Define this distinction without changing existing serial callers. Already-started siblings settle and successful owned patches may survive ordinary failure; strict structural conflicts remain fatal.
5. **Result diagnostics at the adapter seam.** `workflowDriver` serializes `result.state` and returns that state as `structured`; it currently discards the detailed `stepResults` from its public driver output (`drivers.ts:137-151`). It also maps workflow cancellation to empty text (`drivers.ts:128-134`). Tests may inspect direct Workflow results and a complete host ledger; eval cannot infer node attempts, blocked dependencies or repair counts from final state alone. Add bounded optional diagnostics only if a real public consumer requires them; avoid making new graph metadata mandatory state fields.
6. **Continuation boundary.** Reuse v2 checkpoints only for an entirely completed graph group or a validated serialized top-level boundary. They cannot encode an arbitrary completed node set/ready frontier. Restoring inside a group requires a separate versioned contract and effect-reconciliation design. Graph changes inside a stable named group must bump `definitionVersion`, because the existing ordered-name binding cannot detect edge/callable changes.
7. **Retry ownership.** Ordinary standalone retry and controlled acknowledgement handling differ. Graph retries must not multiply Workflow retry, Agent retry and provider SDK retry layers, or rerun an acknowledgement-unknown effect. Host operation intent/receipt reconciliation remains required for uncertain external outcomes. Keep partial outputs/attempt records even when a subsequent repair succeeds.
8. **Public consumption.** Core and harness ship ESM/CJS with separate `.d.ts`/`.d.cts` exports (`core/package.json:23-37`; `harness/package.json:22-48`). Core ships the workflow contract (`core/package.json:81-84`). New public types/docs must resolve through those packed entries; no workspace aliases, mandatory harness/eval import in core-only usage, or new graph dependency should be necessary.

## Proposed acceptance cases

Use deferred gates and complete host effect/attempt ledgers rather than real-time sleeps for ordering assertions. These are proposed checks, not passing results.

| Case | Setup and observable acceptance |

## Feasible measured loop-versus-graph comparison

Use two complementary comparisons. The first isolates the scheduler's behavior against an equivalent structured Workflow baseline. The second compares the ordinary bounded Agent loop with explicit Workflow orchestration under identical task definitions and host budgets. Neither can establish live-model reasoning quality from recorded responses.

**Versioned deterministic manifest.** Add a proposed `execution-graphs-eval.v1` fixture beside the existing harness acceptance fixtures, with fixed task IDs, dependency manifests, inputs, primitive tool implementations/results, injected failures/gates, provider snapshot identifier, prompts/schemas, declared usage, budget/cap/repair limits, expected effects and exact outcome labels. Labels live outside agent-visible input. Use isolated stores/resources/session IDs and reset every scripted provider/ledger between conditions. Key fake provider responses by task/purpose/attempt, not a global request index; scheduling order must not change which task gets which answer.

**Common task execution.** Both conditions call the same primitive task implementation and, where tasks need reasoning, the same bounded Agent/provider configuration through the same `ExecutionServices`. The loop uses existing `agentDriver`; explicit orchestration uses the existing `workflowDriver`. Give the loop the same task/dependency information that is encoded in the graph; do not grant the graph a hidden gold plan. Do not restrict the loop's existing ability to request multiple independent tools. Any additional loop planning calls or graph wrapper-effect admissions are measured as actual overhead and consume the same envelope; do not conceal unequal overhead by comparing node-only counts. Preserve the same permitted logical effect set and document any necessary wrapper grant names.

**Small initial workload.** Use a straight chain, independent fan-out, the G02 shared-prerequisite DAG, branch/join, one-successful-repair, repair exhaustion, cancellation, strict conflict, uncertain acknowledgement and completed-boundary continuation: ten paired scenarios. Configure both conditions with the same finite `maxModelCalls`, `maxToolCalls`, `maxTokens`, `maxRevisions`, Agent roundtrip/output limits and cancellation deadline; use a declared maximum graph concurrency of 2. A reasonable fixture envelope can start at 12 logical model calls, 12 tool/effect admissions and 16,000 declared total tokens per case, provided fixture preflight proves both sides' intended successful traces fit. These are proposed fixture ceilings, not optimal production settings or authorized live spend. Run each pair in both controlled settlement orders for 40 condition executions; deterministic repeats test ordering invariance, not statistical model variance. No judge model or paid calls are needed.

**Measurements and exact checks.** Record normalized task success/final state; dependency violations; forbidden/duplicate effects; node/task/repair attempts; started/completed/skipped/blocked counts; statuses and reasons; model calls; tool/effect admissions; declared/reported tokens; peak simultaneous task/provider calls; remaining/reserved budget; unknown usage; cancellation and cleanup coverage. Count orchestration/planning/verification separately from primitive task work while including all of them in totals. Preserve raw outputs and complete ledger traces, including failures. `createHarnessEvalTarget.observation()` supplies budget/native status/tool coverage; collect graph task boundaries using a test-owned complete ledger because `workflowDriver` does not expose detailed step results in its output. The existing eval suite's `total`, `gradedCases`, `infrastructureFailures` and output-retention fields can preserve coverage; exact host checks should be ordinary deterministic scorers, not an LLM judge.

**Timing.** Use virtual gate schedules to report fixture critical-path/overlap behavior and verify G02. Clearly label any synthetic duration as fixture scheduling latency. If a local benchmark is later authorized, use the same fixed gate/delay workload and report measured orchestration wall-time overhead separately, predeclare repeats and retain every run; do not interpret fake-provider delay differences as live model throughput. Real provider latency, billing and task quality remain unmeasured here.

**Decision contract.** Any forbidden effect, dependency violation, duplicate unknown-outcome effect, leaked reservation, false successful partial result, cancellation admission or unsafe checkpoint restoration blocks irrespective of averages. Every successfully executable baseline task must retain the exact normalized outcome under graph orchestration. The graph should demonstrate the G02 overlap without duplicate primitive work. Report per-case call/token/overlap differences and graph overhead; do not assume an improvement beforehand. An infeasible baseline or missing/incomplete observation is explicit coverage, not a dropped denominator or pass. The fixture suite demonstrates covered SDK invariants and structural overhead, not model superiority, production reliability percentages or release readiness.

Live model comparison is a later separately bounded experiment with pinned snapshots/sampling/tool versions, matched prompts/tasks/budgets, predeclared repeated paired cases, calibrated outcome scoring and an uncertainty/inconclusive policy. No live result or speed/cost advantage is claimed in this inventory.

## Challenge notes for the parent candidate contract

Candidate supplied during this investigation: additive `GraphStep.graph` accepts a node array or synchronous state-derived factory; `maxNodes` defaults to 100, `maxConcurrency` to 5, and new graph merge defaults to `error` with `declaration_order` available. Nodes have `id`, existing `StepDef`, control `dependsOn` and data `inputsFrom`; control prerequisites admit done/skipped, while data prerequisites require done and contribute transitive data-ancestor patches. Additive `RepeatStep` has nested steps, a `(state, iteration)` predicate and positive finite `maxIterations`. Generated executable steps remain host-authored/registered; services/budgets and outer checkpoint boundaries are reused. This is still a proposal, not implemented or verified behavior.

This candidate stays within the existing ownership architecture. The following details should be frozen before tests/implementation:

| Gap | Required observable rule/acceptance addition |
| --- | --- |
| Data-only reference readiness | `inputsFrom` contributes a dependency even when the same ID is absent from `dependsOn`. Validate missing references/self references/cycles over the union of control and data edges before any generated node effect. Test a blocked data-only predecessor and a cycle spanning one control plus one data edge. |
| Skipped/error prerequisites | Done/skipped control readiness and done-only data readiness are separate and must be documented. A skipped data ancestor blocks/skips the consumer; an error predecessor never admits a success-requiring consumer. Run true/false conditional predecessors for both edge kinds and retain the reason for skipped descendants. |
| Node identity versus step name | Existing state and effect/diagnostic names are based on `step.name`, not the proposed node `id` (`types.ts:64-70`; workflow README:3; harness README:315). Unique node IDs alone do not prevent duplicate `${step.name}_output`, ambiguous step results or ambiguous `workflow:<stepName>` grants. Require an unambiguous scope/mapping and test duplicate step names under different IDs without changing ordinary step naming. |
| Ancestor patch provenance | A shared ancestor reached by two `inputsFrom` paths must contribute its owned patch once. Copied/transitive state snapshots are not additional writers. Test A feeding B/C and both feeding D; D must not raise a false A-versus-A conflict. |
| Ordered versus incomparable writes | Decide whether strict conflict covers incomparable writers only, or all distinct writers even when explicitly ordered. Intentional successor overwrite of an ancestor key must have a documented usable path. Test A writes `n`, B consumes A and writes `n`, versus independent A/B writes. State visibility and final-state ordering must not depend on settlement timing. |
| Changed merge default | New graph default `error` is an opt-in graph contract, while existing parallel default remains declaration order. Run both forms side by side in public/packed fixtures and document that distinction. |
| Materialization bounds | Validate array/factory output, `maxNodes` and `maxConcurrency` as finite safe integers before generated effects; reject unsupported asynchronous factory output. The cap applies to each materialization and the design must disclose the overall finite bound from nested repeats/materializations. Do not hide potentially large products of iteration/node limits, and never reset global model/tool/token budgets. Test factory output at and above the cap on a later iteration. |
| Repeat entry/exit/cap | Define iteration numbering and predicate timing. A false entry predicate executes zero children. After the last permitted iteration, false means normal completion and still true means explicit exhaustion, with no extra child admission. Reject nonboolean runtime predicate output. Test exactly-at-cap success, always-true cap exhaustion, predicate throw, cancellation and child failure. |
| Repeat outcome propagation | Existing public Workflow aggregate reason is typed only as `workflow_step_failed` (`types.ts:58-59`) and the adapter only specially catches cancellation (`drivers.ts:128-134`). Choose how an explicit repeat-limit code remains available through direct Workflow and harness/eval without changing existing status meanings. It must not become completed or a message-only reason that callers must parse. |
| Repeated identity/effects | Retain unambiguous node/iteration/attempt observations while repeated logical names remain stable for host grants. An intentional new iteration and retry of one acknowledgement-unknown intent are different; only the host can authorize/reconcile the latter. Do not infer effect safety from a new graph visit or run ID. |
| Factory/definition continuation identity | Version the factory, edge-generation policy and registered callable dependencies through the host-owned `definitionVersion`. Top-level v2 names cannot fingerprint generated nodes. Resume only after the complete graph/repeat group; never claim it restores an active iteration or prior per-node reservations. |
| Planner authority | If an optional model proposes topology, it proposes bounded IDs/references into the registered host step set. Invalid/unregistered IDs and over-cap output fail before execution. Planner calls use existing controlled services, model grants and aggregate budgets; serialized model text cannot become arbitrary executable functions or host authority. |

The earlier comparison envelope used a declared concurrency of 2 to keep both sides' scheduling observable; it need not adopt the candidate's default 5. Freeze the candidate's explicit defaults and validation semantics in the manifest so a future default change cannot silently alter paired cases.
